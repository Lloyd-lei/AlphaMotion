# JEPA 和 MSBA 到底在算什么——大白话 + 真实数字

所有数字来自实际加载 `V9_jepa_pt_0808` / `V9_arclen_pt_0808` / `V7_maskfsq_0807` 的checkpoint跑出来的，不是从代码描述推的。

---

## 0. 两条臂共同的处境

一段动作进来：**60帧 × 6个关键关节 × 9个数**（3×3旋转矩阵拉平）= 每帧54个数，整段3240个数。

要压成：**9个register × 6维 × 5档**。

一个register能装多少信息？6维每维5档 → $6\times\log_2 5 = 13.932$ 比特。九个 = **125.38比特/窗口**。60帧@30fps = 2秒，所以 **62.69 bit/s**。

**3240个浮点数 → 125.38比特。** 这是两条臂完全相同的处境，而且代码里有 `assert abs(total_bits_per_s - 62.69) < 0.01` 在第一步训练前就跑，**配置不对的臂物理上进不了判决表**。

两条臂的区别只有一件事：**这9个register各自负责什么。**

---

## 1. 先说共同的第一步：每帧变成一个token

```
w              (1, 60, 6, 9)     原始动作
   ↓  三个Linear: 绝对姿态 + 速度 + SG5平滑加速度，相加
   ↓  加上时间编码，进5层Transformer（跨帧self-attention）
frame_h        (1, 60, 256)      每帧一个256维token
```

到这里两条臂一模一样。**60个token，每个都"看过"了整段动作**（self-attention是全连接的）。

---

## 2. JEPA：8个"摘要员"各自去问整段

```
context: 第0帧和第59帧  →  ctx_enc  →  2个token   ← 端点单独编码
                                    ↓
path_q (8个可学习query) ──cross-attend──► [60个帧token ; 2个端点token]
                                    ↓
path_f         (1, 8, 6)      8个latent，各6维
   ↓ FSQ量化（每维夹到5档之一）
path_q         (1, 8, 6)      整数码，例如 [2,2,3,1,2,2]
+ time_f       (1, 1, 6)      第9个register：从弧长曲线算出的"时长档位"
```

**关键点一：8个query是无序的、并行的、永远全部在场。** 没有"第1个register最重要"这种顺序，8个一起算出来。

**关键点二：latent是"条件式"的。** 端点（第0帧、第59帧）已经单独喂给了解码器，所以这8个latent**不用花比特去重述端点**。

解码器的baseline是**两个端点之间的直线插值**（在旋转流形上），网络只预测**相对这条直线的偏差**。所以125比特全花在"路径怎么弯"上，一个比特都不浪费在"起点终点在哪"。

**关键点三：`--w_jepa` 这一项。** 解码器的逐帧latent还要在stop-grad下去匹配编码器的逐帧特征。代码注释写得很直白：

> 没有这一项它就是个 conditional VQ-VAE，叫JEPA就是撒谎

---

## 3. MSBA：9个"值班员"各管一段，只准看自己那段

```
frame_h        (1, 60, 256)
   ↓
把60帧切成8个连续组，每组7-8帧：[8, 7, 7, 8, 8, 7, 7, 8]
   ↓
grp_q (8个query) ──cross-attend──► 帧token
   但 lg.masked_fill(~group_mask, -inf)
   ↓  第5组的query只能看第32-39帧，别的帧的注意力权重被强制为0
g              (1, 8, 256)   → 再过2层Transformer让组之间通气
   ↓ FSQ
path_q         (1, 8, 6)     例如第0组 [4,4,4,0,0,2]
+ time_f       (1, 1, 6)     速度token（V8/arclen加的，maskfsq原版没有）
```

**核心机制就是那一行 `masked_fill`**：第5个register的query在算注意力时，除了第32-39帧以外所有位置都被填成 $-\infty$，softmax之后权重为0。**它物理上看不见别的帧。**

编码器输入还会**随机遮掉一部分帧**（`mask_tok`），逼着它学会从残缺输入恢复。

### V8/arclen 只改了一件事：切的是"路程"不是"时钟"

maskfsq按**时钟**均分（每组7-8帧）。arclen先做 `_arc_regrid`：把60帧按**累积路程**重采样——走得慢的地方帧被拉稀，走得快的地方帧被压密。然后同一套机器原样跑，所以"连续组"变成"连续的**路程**切片"。

代码注释里的实测说明了为什么这是个权衡：

> 等时钟切片在全部6个族上重建都更好（run 5.16 vs 5.56 cm）**因为等路程会饿死慢速段**；但等路程才是能在时间扭曲下存活的。最优值应严格在两端之间，所以它是个扫描参数而不是常量。

`arc_alpha` 就是这个旋钮，0=纯时钟，1=纯路程。

## 4. 你最关心的：解码时会不会掉分辨率？——不会

```
DECODE T_out=60    →  (1, 60, 6, 9)
DECODE T_out=240   →  (1, 240, 6, 9)   ← 同一批码，输出240帧
```

**解码器不是"9个点插值回60帧"。** 机制是：生成 `T_out` 个**逐帧时钟query**，每个query去 cross-attend 全部9个register + 2个端点，各自算出自己那一帧。

`T_out` 是自由参数（query用 `fourier_time` 连续编码），**你想要多少帧就给多少帧，包括比输入更密**。

**所以"不想要池化/下采样"这个担忧，在输出侧不成立。** 池化只发生在瓶颈写入端。这和audio codec不一样——audio codec的decoder常常真的是转置卷积上采样，那里"分辨率损失"是字面意义的；这里每一帧都有独立query。

**真正限制精度的是62.69 bit/s这个预算，而两条臂完全相同。** 换成JEPA一点都不会缓解。

## 5. 一个具体计算：局部改动会影响哪些码

我拿一段平滑动作，**只在第40-49帧上多叠一个0.35弧度的旋转**，看哪些register的整数码变了（6位数字里变了几位）：

| arm | 变化的register | 每个register变了几位 |
|---|---|---|
| **maskfsq**（时钟组） | 8/9 | `[1, 0, 1, 2, 1, 1, **3**, **5**, 1]` |
| **arclen**（路程组） | 7/8 | `[1, 1, 2, 1, 3, **4**, 3, 0]` |
| **jepa**（全局） | 8/8 | `[1, 1, 2, 1, 2, 2, 1, 4]` |

**看分布，不是看"变了几个"**：

- maskfsq 的变化**集中在第7、8个register**（3位和5位），那正是拥有第40-49帧的那两组
- arclen 的峰值在第6个register
- **jepa 是均摊的**（1,1,2,1,2,2,1,4），没有哪个register特别负责那一段

这就是 `exam_partial.py` 说的 **code locality**。它不是"完全不影响别的register"（组之间还有2层Transformer通气，而且量化边界会放大微小扰动），而是**改动的能量集中在负责那段的码上**。

### 一处我最初测错了、值得你知道的坑

我第一次用**随机噪声**动作测，结果是 arclen 全部8个register都变（每个变4-6位），jepa只变1位。**那个结果是等弧长重采样的副作用**：随机噪声下改任何一段都会大幅改变整条累积路程曲线，于是**所有节点的采样位置都移动了**，看起来像"全局影响"。

换成平滑动作（真实动作的性质）之后局部性才显现。**这说明 arclen 的局部性依赖于"路程曲线不被局部改动大幅扰动"——对平滑动作成立，对抖动剧烈的动作会退化。** 这个性质我在文档里没看到有记录。

## 6. 这个局部性带来什么功能——实测数据

`T32_partial.txt`，括号里是**相对该臂自己无遮挡误差的退化量**：

| 可见帧 | 模式 | JEPA 退化 | **MSBA 退化** |
|---|---|---|---|
| 8 | prefix（只有开头） | +5.11 | **+3.51** |
| 30 | prefix | +4.68 | **+1.67** |
| 45 | prefix | +2.42 | **+0.44** |
| 8 | **sparse（随机关键帧）** | +4.10 | **+0.60** |
| 15 | sparse | +3.60 | **+0.12** |
| 30 | sparse | +2.40 | **−0.02** |

**sparse那一列是决定性的**：给30个随机关键帧，MSBA退化 **−0.02**（等于没退化），JEPA是 +2.40。

而这正是你要的核心功能——**"我只指定几个关键帧，其余你补全"**。

顺带纠正一个我们之前都说错的：`exam_partial.py` 注释里写着 —— **"jepa只能往后预测"是错的，`grep causal/triu/tril` 在 `train_v7.py` 里零命中，两条臂都是全双向。** 区分它们的轴是 code locality，不是方向性。

## 7. 汇总对照

| | JEPA | MSBA（maskfsq / arclen） |
|---|---|---|
| 9个register各管什么 | 8个全局latent + 1个时长档 | 8个各管一段连续切片 + 1个速度token |
| 注意力范围 | 每个query看整段 | **`masked_fill` 强制只看自己那段** |
| 稀疏关键帧补全 | +2.4~4.1cm 退化 | **≈0 退化** |
| 局部编辑 | 改动均摊到所有码 | **改动集中在对应组** |
| 流式/因果化改造 | 8个latent需完整窗口 | **组码可增量产出** |
| warp不变性 | 0.8668 / 0.839 / 0.8786 | **0.9221 / 0.8956 / 0.9302**（arclen族） |
| 输出分辨率 | `T_out` 自由 | `T_out` 自由 |
| 比特预算 | 62.69 bit/s | 62.69 bit/s（断言强制） |

**MSBA在功能性上全面占优，JEPA没有留下结构性优势。** 早期maskfsq在warp不变性上的0.542是**时钟网格版**的问题，V8换成等弧长坐标正是为了修它——修好了（0.9221），并且保住了code locality。这也解释了 `V9_arclen_pt_0808` 为什么是唯一三门全过的arm。

## 8. 既然池化不是精度瓶颈，真正该盯的两处

**一、速度token其实是幅度token。** 代码注释里的实测：线性探针从训练好的速度token读出**总路程长度 R²=0.87–0.96，比读出时间形状（0.85–0.88）还高**。后果是移植一个速度token会改变**路径**而不只是节奏（dance在弧长对齐后仍有12.88cm形状漂移）。`--pure_timing` 是修复，但**没登记进 `MODEL_VERSIONS.md`**，而此前所有"速度不变性"数字都受这个污染。

**二、码本变大会伤零样本。** S3用+60%比特，human侧买到0.20cm，**零样本侧付出0.18cm**（6.61→6.79，四个扫描臂单调反向）。`RUNS_INDEX.md` 只记了human那半，记成"边际递减"——实际是**过拟合拐点**，两个诊断给出的行动相反。

对机器人安全来说，这两条比池化重要得多：前者意味着你以为在调节奏其实在改轨迹，后者意味着堆比特会让没见过的机器人更差。
